## 1. Problem Formulation

이 논문은 **LLM multi-agent system의 추론 시 병렬화를 두 층의 decision process로 정식화하고, 두 층을 하나의 실행 framework 안에서 조합해 accuracy, latency, token 비용의 trade-off와 적용 한계를 체계적으로 밝히는 것**을 목표로 한다. Magentic-One류의 multi-agent system은 agent들이 차례로 LLM과 tool을 호출하고 중간 상태를 주고받는 직렬 조정으로 동작하므로, round가 늘수록 critical path가 길어지고 context가 희석되며 오류가 전파된다. 이를 완화하는 병렬화는 이미 두 갈래로 존재한다. M1-Parallel처럼 여러 team을 동시에 돌려 해법 경로 자체를 여러 개 탐색하는 방식은 정확도를 올리지만 token을 배로 쓰고, LLMCompiler처럼 한 경로 안의 subtask를 dependency graph로 풀어 동시에 실행하는 방식은 latency를 줄이지만 경로 하나의 품질에 묶인다. 두 방식은 각자 따로 연구되어, 서로 어떤 관계인지와 합치면 보완적인지 충돌하는지가 밝혀지지 않았다. 저자들은 전자를 Replica Parallelism, 후자를 Structural Parallelism으로 이름 붙이고, 두 층을 통합된 실행 semantics 아래에서 조합하고 분석할 수 있는 framework **TIPEX**(Two-tier Inference-time Parallel EXecution)를 제안한다.

- **입력**: user query $$q$$. replica 수 $$n$$, replica 생성 전략(RIG / OHG), 선택 전략(GS / FVES / TKS), 구조 병렬 정책(SS / BP / AP)이 설정 변수이다.
- **출력**: 각 replica $$x_i$$의 결과 tuple $$r_i = (s_i, a_i, \tau_i)$$(성공 여부, 답, 실행 trace)와, 그중에서 judge가 고른 최종 답 $$A^\ast$$
- **최종 목표**: 동일한 Magentic-One pipeline 위에서 두 층의 설정만 바꿔 가며 GAIA의 accuracy, wall-clock time, token 소비를 재고, 어떤 조합이 어떤 task 영역에서 이득을 주는지의 경계를 찾는다.

## 2. Limitations of Existing Works

**[Serial Coordination]** multi-agent system의 추론은 orchestrator가 agent 하나를 고르고, 결과를 받고, 상태를 갱신하는 iteration의 반복이다. 단계마다 LLM 호출과 tool 대기가 직렬로 쌓이므로 task가 복잡할수록 critical path가 길어진다. 실행 중 관측이 context에 계속 추가되어 초반 정보가 희석되고, 초기 단계의 실수가 이후 모든 단계로 이어진다. GAIA level 3에서 Magentic-One은 task당 평균 772초를 쓴다.

**[Isolated Parallelism]** 기존 병렬화 연구는 설계 공간의 한 부분만 다룬다. M1-Parallel은 team 여러 개를 독립적으로 돌리고 마지막에 답을 고르는 task 수준 병렬화만 본다. LLMCompiler, Plan-over-Graph, DynTaskMAS는 한 경로 안의 function call이나 subtask를 task graph로 만들어 동시에 실행하는 경로 내부 병렬화만 본다. 두 병렬화가 같은 자원을 쓰고 같은 최종 답에 기여하는데도, 하나를 켜면 다른 하나의 효과가 어떻게 달라지는지에 대한 분석이 없다. 결과적으로 실무에서는 "둘 다 최대로 켜면 된다"는 가정 외에 근거가 없다.

**[Diversity by Sampling Only]** task 수준 병렬화의 이득은 replica들이 서로 다른 해법을 시도할 때 나온다. 기존 방식은 같은 prompt를 temperature sampling으로 반복해 다양성을 얻고, M1-Parallel은 prompt로 다양성을 유도해도 반복 sampling보다 낫지 않다고 보고했다. 그러나 이 결과는 "다르게 만들라"는 막연한 요구의 결과이고, 해법 경로, 정보 출처, 검증 방식 같은 축을 명시해 다양성을 설계하는 방법은 시험되지 않았다. 또한 replica가 여러 개일 때 최종 답을 고르는 judge의 품질이 병목이라는 점도 체계적으로 측정되지 않았다.

## 3. Methodology

{% include figure.liquid path="assets/img/posts/tipex/fig2_overview.png" class="img-fluid rounded z-depth-1" zoomable=true %}

[Figure 2] TIPEX 전체 구조이다. (a) Tier-1 Replica Parallelism은 replica 생성(Random Isomorphic 또는 Orthogonal Heterogeneous), 병렬 실행, 선택(validity filtering 후 judge가 Global / First-Valid / Top-K 전략으로 선택)으로 이루어진다. (b) Tier-2 Structural Parallelism은 replica 하나 안에서 LLM이 dynamic DAG를 만들고, scheduler가 frontier node를 Strict Sequential / Balanced / Aggressive 정책으로 실행 unit(agent, tool)에 배정하며, 완료 feedback으로 DAG를 확장한다.

TIPEX는 두 층의 결정을 분리한 계층적 framework이다. 전체 pipeline은 다음과 같다.

- ① **Replica 생성**: query $$q$$에 대해 설정 $$\theta_i$$를 가진 $$n$$개의 solution replica $$x_i \sim \Phi(q, \theta_i)$$를 만든다.
- ② **Replica 실행**: 각 replica는 자기 execution scheduler가 관리하는 dynamic DAG $$G_i = (V_i, E_i)$$ 위에서 agent와 tool 호출을 실행하고 $$r_i = (s_i, a_i, \tau_i)$$를 낸다.
- ③ **선택**: solution orchestrator가 $$\{r_i\}$$를 관찰하다가 선택 전략에 따라 탐색을 멈추고, judge $$J$$가 후보 집합 $$C$$에서 $$A^\ast$$를 고른다.

두 층은 granularity가 다르다. 바깥층은 "어떤 해법 가설들을 탐색하고 어느 것을 믿을 것인가"를, 안층은 "한 가설 안에서 어떤 step들을 동시에 실행할 것인가"를 결정한다.

### 3.1. Replica 생성: RIG와 OHG

replica는 확률적 생성 정책 $$\Phi$$에서 나온다.

$$
x_i \sim \Phi(q, \theta_i), \qquad i = 1, \dots, n
$$

$$\theta_i$$는 $$i$$번째 solver instance의 설정으로, replica 사이의 이질성을 제어한다. $$\theta_i$$를 어떻게 만드느냐에 따라 두 전략이 갈린다.

**Random Isomorphic Generation (RIG).** 모든 replica가 같은 생성 지시를 공유한다($$\theta_1 = \cdots = \theta_n$$). 다양성은 temperature $$T > 0$$의 확률적 decoding에서만 나온다.

$$
x_i \overset{\text{i.i.d.}}{\sim} \Phi(q, \theta), \qquad T > 0
$$

self-consistency를 agent 실행으로 일반화한 것이다. 독립 sample을 여러 개 뽑아 model 분포의 지배적인 reasoning mode를 근사하고, 개별 trajectory의 오류를 평균 낸다.

**Orthogonal Heterogeneous Generation (OHG).** meta-reasoning으로 서로 의미가 다른 해법 전략을 명시적으로 합성한다. 여기서 orthogonal은 수학적 직교 대신 방법론적 다양성을 뜻한다.

$$
\{\theta_1, \dots, \theta_n\} \leftarrow \mathrm{Synthesize}(q, \text{facts}, \text{team}, n)
$$

strategy synthesizer는 query, 알려진 facts, team 구성, 필요한 개수를 받아, 해법 경로(path), 정보 출처 선호(source), 검증 방식(validation), 위험 선호(risk) 같은 축에서 서로 다른 전략을 만든다. Figure 1의 세 전략이 그 예로, 하나는 CSV를 직접 읽고 하나는 LLM 추정에 의존하며 하나는 두 조회를 동시에 한다. replica가 random seed 수준을 넘어 문제 해결 논리 자체에서 갈리므로, 저자들은 이를 structured complementarity라 부른다. 즉 **RIG는 같은 분포에서 여러 번 뽑고, OHG는 분포 자체를 여러 개 설계한다.**

### 3.2. 선택: Validity Filtering과 Judge

선택은 두 단계이다. 먼저 runtime exception 없이 끝났고 형식이 갖춰진 답과 trace를 낸 replica만 후보 집합 $$C$$에 넣는다. 그 다음 judge 연산자 $$J$$가 각 후보에 점수를 매기고 최대값을 고른다.

$$
x^\ast = \arg\max_{x_i \in C} S(a_i, \tau_i \mid q)
$$

$$S$$는 LLM 기반 의미 평가와 결정적 검사를 합친 점수이다. judge는 별도의 LLM evaluator로 구현되며 답의 확정성(definiteness), 근거의 강도(evidence strength), 추론의 일관성(reasoning consistency)을 채점한다. 언제 $$J$$를 부를지에 따라 세 orchestration 전략이 있다.

- **Global Selection (GS)**: $$n$$개 replica가 모두 끝날 때까지 기다린 뒤 전체 후보에 $$J$$를 적용한다. 후보가 가장 많지만 latency는 가장 느린 replica에 묶인다.
- **First-Valid Early Stopping (FVES)**: validity filtering을 통과한 첫 replica를 그대로 반환한다. $$J$$의 비교 없이 즉시 끝나므로 latency가 가장 짧다.
- **Top-K Selection (TKS)**: 유효한 후보가 $$k$$개 모이면 그 부분집합에만 $$J$$를 적용한다. 기본값은 $$k = \lceil n/2 \rceil$$이다.

GS는 coverage를, FVES는 속도를 취하고, TKS는 그 사이에서 "충분히 모였을 때 비교한다"는 절충이다. 따라서 선택 전략은 **judge에 후보를 몇 개, 언제 보여 줄 것인가**의 결정이며, judge 자체의 정확도는 세 전략 모두의 상한이 된다.

### 3.3. Structural Parallelism: Dynamic DAG와 세 가지 Scheduling 정책

한 replica 안의 실행은 online으로 전개되고 중간 결과에 따라 다음 step이 달라진다. 그래서 저자들은 실행을 미리 고정된 task graph 대신 부분 관측 아래에서 단조 증가하는 DAG의 확장과 scheduling으로 모델링한다. replica $$i$$는 시각 $$t$$에 DAG $$G_i^{(t)} = (V^{(t)}, E^{(t)})$$를 유지한다. node는 LLM 추론이나 tool 호출 같은 원자적 계산 단위이고 edge는 엄격한 data 또는 논리 의존성이다. 매 시각 scheduler는 실행 가능한 frontier를 찾는다.

$$
F^{(t)} = \{\, v \in V^{(t)} \mid v \text{ is causally ready at } t \,\}
$$

부모 node가 모두 DONE인 node들이 frontier이다. 이 frontier를 어떻게 소비하느냐가 세 정책이다.

- **Strict Sequential (SS)**: 원래 agent trajectory 순서대로 한 번에 node 하나만 실행한다. 구조 병렬화가 없는 baseline이다.
- **Balanced Parallelism (BP)**: 원래의 high-level task 분해를 유지한 채, 자연스럽게 분리되는 subtask들, 즉 frontier의 독립 node 전부를 동시에 실행한다.
- **Aggressive Parallelism (AP)**: workflow를 더 잘게 쪼개 병렬 가능한 subtask를 늘리고, frontier보다 많은 node를 speculative하게 실행한다.

node 실패는 지역적으로 처리된다. 제한된 횟수만 retry하고, hard dependency가 실패하면 그 사슬만 종료하며 독립된 branch는 frontier를 따라 계속 진행한다. 실행 unit의 PENDING → DONE feedback이 DAG builder로 돌아가 다음 node가 생성된다. AP는 critical path를 더 압축할 수 있지만, 아직 준비되지 않은 정보로 node를 실행하므로 중복 실행과 정보 통합의 약화를 낳을 수 있다. 결과적으로 구조 병렬 정책은 **"frontier를 얼마나 공격적으로 비울 것인가"**의 연속선 위에 있고, 그 대가는 4장에서 수치로 드러난다.

### 3.4. 두 층은 왜 독립적인 knob이 아닌가

두 층은 같은 자원을 쓰고 같은 최종 답을 만든다. replica를 늘리면 각 replica의 실행 시간이 그대로 latency로 쌓이므로, 구조 병렬화가 replica 증가의 시간 비용을 얼마나 흡수하느냐가 replica scaling의 실효를 정한다. 반대로 구조 병렬화를 공격적으로 밀면 개별 replica의 답 품질이 떨어지고, judge가 고를 수 있는 좋은 후보가 줄어 replica 증가의 정확도 이득이 사라진다. TIPEX는 Magentic-One의 agent pipeline을 그대로 두고 두 층의 설정만 바꾸므로 이 상호작용을 통제된 조건에서 잴 수 있다. 저자들의 기본 설정은 OHG, TKS($$k = 2$$), BP, $$n = 3$$이며, 이 조합이 왜 기본값이 되었는지는 4장의 결과로 설명된다. 핵심은 **한 층의 가치가 다른 층의 설정에 따라 달라진다**는 관점이며, 이것이 논문 제목의 two-tier perspective이다.

## 4. Experiments

### 4.1. Setup

benchmark는 GAIA validation set이며 level 1/2/3으로 나누어 본다. baseline은 Magentic-One이고, TIPEX는 그 위에 두 층의 병렬화만 추가한 구현이다. model은 Qwen-Plus, 실행은 Python asyncio의 고동시성 event loop로 구현해 latency 이득이 blocking I/O 우연이 아니라 알고리즘적 병렬화에서 나오도록 했다. level 1과 2는 3회, level 3은 5회 반복한 평균이다. 지표는 accuracy, wall-clock time, token 소비이고, 여기에 **Oracle Accuracy**(후보 $$n$$개 중 하나라도 정답이면 성공, 완벽한 judge 아래의 상한)를 더해 생성 품질과 선택 품질을 분리한다. 부록에서 DeepSeek-v3.2로 GAIA2-mini에 대해서도 같은 정성적 경향을 확인했다고 보고한다.

### 4.2. Main Results

| L2 | Acc. (%) | 25.8 | 25.0 | 28.1 | **38.7** (48.4) | 32.0 (44.0) | 23.1 (42.3) | 30.8 (38.5) |
| L2 | Time (s) | 320.0 | 193.8 | **168.8** | 281.5 | 261.5 | 250.1 | 204.4 |
| L2 | Token (k) | 41.4 | 56.8 | 52.2 | 81.8 | 79.2 | 80.9 | 66.0 |

| L3 | Token (k) | 50.4 | 64.0 | 63.0 | 130.9 | 81.7 | 84.0 | 94.9 |

[Table 1] GAIA level별 결과이다. 구조 병렬 정책은 BP, $$n = 3$$으로 고정하고 생성 전략과 선택 전략을 조합했다. 괄호는 Oracle Accuracy이다. 병렬 구성은 세 level 모두에서 Magentic-One보다 정확도가 높고 latency가 짧다. level 1 정확도는 43.2에서 52~57로, level 2는 25.8에서 최대 38.7로 오르고, 실행 시간은 대부분 구성에서 15~40% 줄어든다. 대신 token은 1.5~2.6배 든다. 조합 중에서는 OHG+TKS가 가장 균형이 좋다. OHG+GS는 정확도가 높지만 latency와 token이 크고, RIG+FVES는 시간은 가장 짧지만 judge 없이 첫 답을 취하므로 level 1에서 39.0으로 baseline보다 낮다. OHG+TKS는 level 1에서 56.5로 최고 근처이면서 시간은 223.9초로 GS보다 짧다. 저자들은 이 결과로 OHG와 TKS를 기본값으로 정했다.

OHG 기반 구성은 실제 정확도와 Oracle Accuracy의 간격이 RIG보다 일관되게 작다. level 1에서 RIG+GS는 56.7 vs 70.0으로 13.3점 차이인데 OHG+TKS는 56.5 vs 60.9로 4.4점 차이이다. OHG가 판별하기 쉬운 서로 다른 관점의 후보를 만들어 judge의 부담을 줄인다는 것이 저자들의 가설이다. 어느 선택 전략에서든 실제 정확도는 Oracle보다 낮으므로, **병렬 탐색의 이득은 정답 trajectory를 만드는 것만이 아니라 그것을 골라내는 judge의 품질에 달려 있다.** 부록의 judge 민감도 실험에서 judge model을 바꾸면 Oracle 대비 회수율이 65.9%에서 78.3%까지 움직인다.

level별로 보면 구조 병렬화의 latency 이득은 어려운 task에서 커진다. level 1에서는 230초 대비 이득이 제한적이지만, level 2에서 320초가 170~280초로, level 3에서 772초가 218~401초로 줄어든다. task가 복잡할수록 내부에 병렬화할 수 있는 node가 많이 드러나기 때문이다. 한편 replica 병렬화의 정확도 이득은 level 2에서 가장 크고(25.8 → 38.7) level 3에서는 작다(9.2 → 11.5). 저자들은 level 2를 두 층이 모두 효과를 내는 "golden stage"로 부른다.

### 4.3. Ablation Study

[Figure 3] (a) BP 고정 아래 replica 수를 1, 3, 5로 바꾼 결과, (b) $$n = 3$$ 고정 아래 구조 병렬 정책을 SS, BP, AP로 바꾼 결과, (c)(d) GS와 FVES 아래에서 replica 수에 따른 시간이다. OHG+TKS 기본 설정이다.

**Replica 수.** replica를 1에서 3으로 늘리면 level 1과 2에서 정확도가 안정적으로 오르지만, 5로 늘리면 이득이 미미하거나 오히려 줄면서 token은 크게 는다. 저자들은 instance가 너무 많으면 지나치게 다양한 전략이 섞여 유효한 해법의 비율이 희석된다고 본다. 시간 측면에서 TKS는 $$n$$이 3에서 5로 가도 latency가 늘지 않거나 오히려 줄어드는데, 신뢰할 만한 부분집합이 모이면 멈추기 때문이다. GS는 $$n$$이 커질수록 시간이 증가하고, FVES는 시간을 줄이는 대신 정확도를 잃는다.

**구조 병렬 정책.** $$n = 3$$에서 SS를 BP나 AP로 바꾸면 실행 시간이 확실히 줄어든다. 그러나 AP에서는 정확도가 크게 떨어지고 token이 늘어난다. level 1에서 SS 약 54, BP 약 53, AP 약 41이다. AP가 시간을 더 줄이는 경우도 있지만 그 이득은 불안정하고, 중복 실행과 scheduling overhead가 이를 상쇄한다.

[Table 2] level 2에서 replica 수와 구조 병렬 정책을 함께 바꾼 결과이다(OHG+TKS, 정확도 %, 시간 s, token k). 두 층이 더해지는 것이 아니라 상호작용한다는 직접 증거이다. replica가 늘어날 때의 시간 비용을 BP와 AP가 SS보다 잘 흡수한다($$n = 5$$에서 SS 207초, BP 188초, AP 174초). 한편 replica 증가의 정확도 이득은 구조 정책에 좌우된다. BP 아래에서는 $$n$$이 1에서 5로 갈 때 정확도가 29에서 37로 오르지만, AP 아래에서는 28에서 25로 떨어진다. 즉 **Replica Parallelism의 정확도 이득은 Structural Parallelism이 조절하고, Structural Parallelism의 latency 이득은 replica 규모에 따라 달라진다.**

**Task 유형.** level 2를 web, code, multimodal, file로 나누어 combined(두 층 모두), replica-only, structural-only를 비교하면 유형마다 유리한 조합이 다르다. web과 file task는 combined가 가장 좋고(file: 65.0 vs 54.6 vs 40.0), code task는 structural-only가 가장 좋으며(32.3 vs 28.2 vs 25.3), multimodal은 replica 탐색에 더 의존한다(12.6 vs 12.0 vs 7.1). 병렬화 수준을 고정하지 않고 task 구조에 따라 정해야 한다는 근거이다.

**실패 분석.** level 1~3의 실패 104건을 분류하면 reasoning/computation 오류 64건, 정보 검색 오류 24건, 오류 전파 11건, 중복 실행 5건이다. 병렬화만으로는 추론, 검색, 검증 능력을 대체할 수 없고, 중간 검증과 경로 다양성 제어가 필요하다는 것이 저자들의 해석이다.

## 5. Conclusion

**Contribution**

- **[Two-tier Formalization]** 추론 시 병렬화를 task 수준의 Replica Parallelism과 경로 내부의 Structural Parallelism이라는 두 decision level로 정식화하고, 이를 구조화된 설계 공간으로 다룬다.
- **[TIPEX Framework]** 두 층을 하나의 실행 semantics 아래 통합한 제어 가능한 framework를 제안한다. 생성(RIG/OHG), 선택(GS/FVES/TKS), scheduling(SS/BP/AP) 전략을 agent pipeline 수정 없이 조합할 수 있다. GAIA에서 OHG+TKS+BP($$n=3$$)가 Magentic-One 대비 level 1 정확도 43.2 → 56.5, level 2 시간 320초 → 262초를 기록한다.
- **[Interaction and Boundaries]** 두 층이 비가산적으로 상호작용하고(BP는 replica의 정확도 이득을 보존하지만 AP는 무효화), parameter 효과가 비단조적이며($$n$$ 3 → 5, BP → AP에서 이득 소멸), 이득이 task 난이도와 유형에 따라 달라진다는 것을 보인다. 병렬화는 최대화 대상이 아니라 조절 knob이라는 결론으로 이어진다.

**Limitations**

- **[Judge Bottleneck]** 모든 구성에서 실제 정확도가 Oracle Accuracy에 못 미치고, judge model을 바꾸면 회수율이 65.9%에서 78.3%까지 움직인다. 저자들은 judge 품질을 실질적 병목으로 명시하며, 이 한계가 OHG(판별하기 쉬운 후보 생성)와 TKS(후보 수 제한)를 기본값으로 택한 이유가 된다.
- **[Fixed Configuration]** 본 실험은 해석 가능성을 위해 설정을 고정했고, task에 따라 두 층의 parameter를 고르는 Auto Router는 부록의 예비 실험에 그친다. Auto Router는 시간을 262초에서 199초로 줄이지만 정확도는 32.0에서 28.1로 떨어진다.
- **[Token Cost]** 정확도와 latency 이득은 모두 token 증가로 산 것이다. OHG+GS는 level 3에서 baseline의 2.6배 token을 쓴다. GAIA2에서도 더 큰 이득이 더 큰 token 비용과 함께 나타난다.
- **[Reasoning Errors Dominate]** 실패의 62%가 reasoning/computation 오류이다. 병렬화는 탐색 폭과 실행 속도를 바꿀 뿐, 개별 경로의 추론 품질은 바꾸지 못한다.

## 6. 두 층의 병렬화는 어떻게 얽히는가

**Replica Parallelism (M1-Parallel)**

$$
x_i \sim \Phi(q, \theta),\; i = 1..n, \qquad A^\ast = J\!\left(\{a_i\}\right) \text{ or } a_{(1)}
$$

- **"어떤 해법 경로들을 탐색하고 어느 답을 믿을 것인가?"**를 잘 결정한다.
- 하지만 각 경로의 실행은 직렬이라 replica 하나의 latency가 그대로 하한이 되고, replica가 늘수록 judge의 부담이 커진다.

**Structural Parallelism (LLMCompiler, DynTaskMAS)**

$$
F^{(t)} = \{v \in V^{(t)} \mid \text{parents DONE}\}, \qquad \text{execute } F^{(t)} \text{ concurrently}
$$

- **"한 경로 안에서 어떤 step들을 동시에 실행할 것인가?"**를 잘 결정한다.
- 하지만 경로 하나의 품질에 묶여 있고, 공격적으로 밀면 준비되지 않은 정보로 실행해 정확도를 깎는다(BP 32 → AP 29).

**TIPEX**

$$
x_i \sim \Phi(q, \theta_i),\; \{\theta_i\} = \mathrm{Synthesize}(q, \cdot, n), \qquad r_i = \mathrm{Schedule}_{\text{BP}}\!\left(G_i^{(t)}\right), \qquad A^\ast = J(C_k)
$$

- **"replica를 몇 개, 얼마나 다르게 만들고, 각각을 얼마나 병렬로 실행하며, 후보를 몇 개 모아 고를 것인가?"**를 한 framework 안에서 함께 결정한다.
- 하지만 어떤 설정이 좋은지를 아직 사람이 정하며, judge의 상한과 개별 경로의 추론 오류는 그대로 남는다.

따라서 이 논문의 핵심은 단순히 "두 병렬화를 합쳤다"가 아니다. **replica 수와 다양성(Tier-1), 경로 내부의 scheduling 강도(Tier-2), 후보를 언제 몇 개 비교할지(선택)를 같은 pipeline 위에서 독립적으로 바꿀 수 있게 만들어, 한 층의 이득이 다른 층의 설정에 따라 사라지기도 한다는 상호작용을 수치로 드러낸 분석 framework**이다.
