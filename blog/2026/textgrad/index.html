1. Problem Formulation

이 논문은 여러 LLM 호출과 tool로 이루어진 compound AI system을, 도메인별 수작업 없이 자동으로 최적화하는 범용 framework를 만드는 것을 목표로 한다. 신경망은 초기에 같은 문제를 겪다가 backpropagation과 automatic differentiation이 최적화를 turn-key로 만들면서 도약했다. 그러나 LLM 기반 system은 API 뒤의 blackbox model, 검색 엔진, simulator처럼 미분할 수 없는 구성요소로 이루어져 있어 수치 gradient가 흐르지 않는다. 기존에도 LLM을 optimizer로 쓰는 연구(ProTeGi, DSPy 등)가 있었지만 prompt 최적화라는 한 용도에 묶여 있었고, 그 밖의 시스템(code, 분자 구조, 치료 계획)에는 매번 새 방법을 만들어야 했다. 저자들은 LLM이 주는 자연어 비평(“이 변수는 ~하게 고치면 나아진다”)을 textual gradient로 정의하고, 이를 임의의 computation graph를 따라 역전파하는 TextGrad를 제안한다. PyTorch와 같은 abstraction과 syntax를 쓰므로 loss.backward()와 optimizer.step()만으로 어떤 변수든 최적화할 수 있다.

  • 입력: computation graph \(v = f_v(\mathrm{PredecessorsOf}(v)),\; \forall v \in \mathcal{V}\). 변수 \(v\)는 prompt, code snippet, SMILES 문자열, hyperparameter 문자열처럼 구조화되지 않은 데이터이고, 변환 \(f_v\)는 LLM 호출, code interpreter, docking simulator 같은 임의의 함수이다.
  • 출력: 최적화 대상 변수의 갱신된 값. prompt optimization에서는 여러 query에 일반화되는 system prompt, instance optimization에서는 특정 문제의 해 자체(code, 분자, 계획)이다.
  • 최종 목표: 자연어로 명시되거나 unit test와 simulator가 계산하는 objective \(\mathcal{L}\)를, framework의 prompt나 구성요소를 손대지 않고 최소화한다.

2. Limitations of Existing Works

[Hand-crafted Compound Systems] LLM과 symbolic solver, 검색 엔진, code interpreter를 엮은 시스템이 올림피아드 수학이나 실제 GitHub issue를 풀고 있지만, 이 성과들은 도메인 전문가가 손으로 설계하고 heuristic으로 조정한 결과이다. 구성요소가 늘수록 어느 prompt와 어느 중간 출력이 최종 실패에 책임이 있는지를 사람이 추적해야 하고, 시스템마다 튜닝을 반복해야 한다.

[No Gradient through Blackboxes] 지난 15년의 AI 발전은 미분 가능한 함수로 연결된 신경망과 수치 gradient에 기대 왔다. compound system의 구성요소는 API 호출과 외부 tool이라 미분이 정의되지 않고, parameter에 접근해 prompt를 gradient로 튜닝하는 white-box 방법은 closed-source model에 쓸 수 없다. 어느 구성요소를 어느 방향으로 고쳐야 하는지를 알려 주는 신호가 없다.

[Prompt-only Textual Feedback] ProTeGi는 prompt 최적화의 맥락에서 textual gradient 개념을 도입했고, DSPy는 LLM 시스템을 program으로 보고 few-shot demonstration을 bootstrapping해 prompt를 개선한다. 두 방법 모두 최적화 변수가 instruction이나 demonstration이고, 여러 단계로 이어진 graph를 통해 feedback을 전파하거나, 문제의 해 자체(code, 분자)를 변수로 두는 데까지 이르지 못했다.

3. Methodology

[Figure 1] (a) 신경망은 수치 gradient를 역전파한다. (b) LLM, 검색 엔진, tool로 이루어진 blackbox system에는 “이 prompt는 ~하게 고칠 수 있다”는 자연어 gradient를 역전파한다. (c) 입력(Variable), model(BlackboxLLM), loss(TextLoss), optimizer(TGD)가 PyTorch의 Tensor, ResNet, CrossEntropyLoss, SGD에 대응하고, forward, backward, step의 세 줄도 같다. (d)~(g)는 분자, code, 치료 계획, prompt 최적화의 예이다.

TextGrad의 한 iteration은 다음과 같다.

  • ① Forward: graph를 따라 변수를 계산하고 objective \(\mathcal{L}\)를 얻는다. \(\mathcal{L}\)는 LLM의 평가문, unit test 결과, simulator 출력 중 무엇이든 된다.
  • ② Backward: \(\mathcal{L}\)에서 출발해 각 변수의 successor로부터 자연어 feedback을 모아 predecessor로 전파한다. edge마다 LLM 호출 하나가 든다.
  • ③ Step: Textual Gradient Descent(TGD)가 현재 값과 feedback을 LLM에 넣어 변수의 새 값을 만든다.

3.1. Warmup: LLM 호출 두 개짜리 시스템에서의 Chain Rule

가장 단순한 시스템은 prompt로 답을 만들고, 그 답을 평가하는 두 호출이다.

\[\text{Prompt} + \text{Question} \xrightarrow{\text{LLM}} \text{Prediction}, \qquad \text{Evaluation Instruction} + \text{Prediction} \xrightarrow{\text{LLM}} \text{Evaluation}\]

Prompt를 Evaluation에 대해 개선하려면 backpropagation의 유비를 그대로 쓴다.

\[\frac{\partial \text{Evaluation}}{\partial \text{Prediction}} = \nabla_{\text{LLM}}(\text{Prediction}, \text{Evaluation}), \qquad \frac{\partial \text{Evaluation}}{\partial \text{Prompt}} = \nabla_{\text{LLM}}\!\left(\text{Prompt}, \text{Prediction}, \frac{\partial \text{Evaluation}}{\partial \text{Prediction}}\right)\]

\(\nabla_{\text{LLM}}\)은 forward 함수가 LLM 호출일 때의 gradient 연산자이다. 먼저 Evaluation을 근거로 Prediction에 대한 비평을 모으고, 그 비평과 (Prompt → Prediction) 호출을 함께 보고 Prompt에 대한 비평을 만든다. 구현은 하나의 고정된 prompt이다.

\[\frac{\partial \mathcal{L}}{\partial x} = \nabla_{\text{LLM}}\!\left(x, y, \frac{\partial \mathcal{L}}{\partial y}\right) \triangleq \text{LLM}\!\left(\text{"Here is a conversation with an LLM: } \{x \mid y\}\text{. Below are the criticisms on } \{y\}: \left\{\tfrac{\partial \mathcal{L}}{\partial y}\right\}\text{. Explain how to improve } \{x\}\text{."}\right)\]

gradient 객체는 변수가 쓰인 맥락과 LLM의 비평을 합친 텍스트이다. 이 연산자는 응용 도메인에 의존하지 않으며, 한 번 구현되면 모든 LLM 호출에 그대로 쓰인다. 핵심은 chain rule의 합성(∘)을 “하류의 비평을 보여 주고 상류 변수를 어떻게 고칠지 묻는” LLM 호출로 바꾼 것이다.

3.2. Textual Gradient Descent

수치 최적화에서 \(\theta_{\text{new}} = \theta - \partial \mathcal{L} / \partial \theta\)인 것처럼, TGD는 현재 값과 feedback을 받아 새 값을 만든다.

\[x_{\text{new}} = \mathrm{TGD.step}\!\left(x, \frac{\partial \mathcal{L}}{\partial x}\right) \triangleq \text{LLM}\!\left(\text{"Below are the criticisms on } \{x\}: \left\{\tfrac{\partial \mathcal{L}}{\partial x}\right\}\text{. Incorporate the criticisms, and produce a new variable."}\right)\]

뺄셈이 “비평을 반영해 다시 써라”로 바뀐 것이고, 이 optimizer 역시 도메인과 무관하게 동일하다. 즉 TextGrad의 두 핵심 연산(gradient 연산자와 TGD)은 각각 하나의 범용 meta-prompt이며, 사용자는 objective만 정의하면 된다.

3.3. 일반화: 임의의 Computation Graph

변수 \(v\)가 여러 곳에서 쓰이면 각 successor \(w\)로부터 온 feedback을 모두 모은다.

\[\frac{\partial \mathcal{L}}{\partial v} = \bigcup_{w \in \mathrm{SuccessorsOf}(v)} \nabla_f\!\left(v, w, \frac{\partial \mathcal{L}}{\partial w}\right), \qquad v_{\text{new}} = \mathrm{TGD.step}\!\left(v, \frac{\partial \mathcal{L}}{\partial v}\right)\]
  • \(\nabla_f\): 변환 \(f\)에 대한 gradient 함수. LLM 호출이면 3.1절의 연산자, simulator면 그 출력을 해석하는 별도 함수이다.
  • \(\bigcup\): 수치 backprop에서 여러 경로의 gradient를 더하는 것에 해당한다. 변수가 쓰인 모든 맥락의 비평이 집합으로 쌓인다.

식은 \(\mathcal{L}\)에서 원하는 변수까지 재귀적으로 적용된다. edge가 \(n\)개인 graph에서 한 iteration의 gradient 계산은 최대 \(n\)번의 추가 LLM 호출이다. objective는 미분 가능할 필요가 없고 정의역과 공역이 비구조 데이터여도 된다. 예를 들어 code에 대한 loss는 “이 code와 목표를 보고 정확성과 시간 복잡도를 평가하라”는 LLM 호출이고, 분자에 대한 loss는 docking simulator의 Vina score와 RDKit의 QED를 LLM에 넣은 것이다.

3.4. Instance Optimization과 Prompt Optimization

TextGrad가 다루는 문제는 두 부류이다. instance optimization은 문제의 해 자체(code snippet, 과학 문제의 답, 분자, hyperparameter 문자열)를 변수로 두고 test time에 그 하나를 개선한다. loss가 ground truth 없이 self-evaluation으로 정의되므로 test-time training과 같은 형태가 된다. prompt optimization은 여러 query에 걸쳐 잘 작동하는 system prompt를 찾는 것으로, 소수의 학습 예시에서 minibatch로 gradient를 모으고 일반화를 목표로 한다. 두 부류 모두 framework를 손대지 않고 같은 세 줄로 실행된다.

최적화 기법도 유비를 따라 옮겨 온다. batch optimization은 여러 instance의 loss를 tg.sum으로 합치고 backward에서 gradient를 이어 붙인다. constrained optimization은 “마지막 줄은 ‘Answer: $LETTER’ 형식이어야 한다” 같은 자연어 제약을 optimizer에 준다. momentum은 TGD가 변수의 이전 iteration들을 함께 보게 한다. 따라서 TextGrad는 수치 최적화의 도구들을 텍스트 공간으로 옮겨 오는 틀이며, 그 위에 어떤 기법을 얹을지는 열려 있다.

4. Experiments

4.1. Setup

다섯 응용을 같은 framework로 실행한다. code 최적화(LeetCode Hard, gpt-4o), 과학 문제 풀이(GPQA diamond, MMLU Machine Learning과 College Physics, gpt-4o), prompt 최적화(BBH Object Counting과 Word Sorting, GSM8k, forward는 gpt-3.5-turbo이고 gradient는 gpt-4o), 분자 설계(DOCKSTRING 58개 표적, Autodock Vina와 RDKit), 방사선 치료 계획(전립선암 환자 5명, matRad). 처음 세 개는 baseline이 있는 benchmark이고, 나머지 둘은 proof-of-concept이다.

4.3. 추가 분석

논문은 구성요소를 하나씩 제거하는 ablation을 두지 않는다. 대신 다음 두 가지가 방법론의 주장을 뒷받침한다. 첫째, prompt 최적화에서 instruction만 고친 TextGrad가 demonstration 8개를 고른 DSPy와 같거나 높은 정확도를 더 짧은 prompt로 얻는다. 이는 3.4절의 두 부류 중 prompt optimization이 few-shot 없이도 작동함을 보인다. 둘째, 치료 계획에서 gradient가 PTV와 장기 사이를 번갈아 조정하는 궤적(Figure 3a)은 3.3절의 gradient가 forward에 numerical solver가 끼어 있어도 의미 있는 방향을 준다는 것을 보인다. 두 실험 모두 gradient 연산자와 TGD의 prompt는 다른 응용과 동일하다.

5. Conclusion

Contribution

  • [Automatic Differentiation via Text] LLM의 자연어 비평을 gradient로, chain rule을 “하류 비평을 보고 상류 변수를 고칠 방법을 묻는” LLM 호출로 정의해, 임의의 computation graph에 대한 backpropagation을 만들었다. gradient 연산자와 TGD는 도메인 무관한 meta-prompt 하나씩이다.
  • [PyTorch Abstraction] Variable, BlackboxLLM, TextLoss, TGD와 forward/backward/step의 syntax를 PyTorch와 맞춰, batch, constraint, momentum 같은 최적화 기법을 유비로 옮겨 올 수 있게 했다. framework는 open-source이다.
  • [Instance Optimization across Domains] prompt를 넘어 code(LeetCode Hard 0.31 → 0.36), 과학 문제의 답(GPQA 53.6 → 55.0), 분자(58개 표적), 치료 계획(환자 5명)을 같은 framework로 최적화했다.

Limitations

  • [Limited Operations] 현재 graph 연산은 LLM 호출과 몇 가지 tool에 한정된다. 저자들은 tool use와 retrieval-augmented generation 구성요소로 연산을 확장하는 것을 첫 번째 과제로 든다.
  • [Optimization Stability] 텍스트 gradient에는 variance reduction, adaptive gradient, self-verification 같은 안정화 기법이 아직 없다. 유비가 열어 둔 설계 공간이자 미완의 부분이며, TextGrad 자체로 TextGrad를 meta-learning하는 방향도 future work로 남긴다.
  • [In silico Only] 분자와 치료 계획은 docking score와 matRad 위의 검증이며, 실험적·임상적 평가는 논문 범위 밖이다.
  • [Cost per Iteration] edge마다 LLM 호출이 하나씩 들고, 각 호출은 변수의 맥락과 비평 전체를 입력으로 받는다. graph가 깊어질수록 한 step의 비용이 선형으로 늘어난다.

6. 무엇을 “미분”하는가

Numerical backpropagation

\[\theta_{\text{new}} = \theta - \eta \frac{\partial \mathcal{L}}{\partial \theta}, \qquad \frac{\partial \mathcal{L}}{\partial \theta} = \frac{\partial \mathcal{L}}{\partial h} \frac{\partial h}{\partial \theta}\]
  • “parameter를 어느 방향으로 얼마나 움직일 것인가?”를 정확히 계산한다.
  • 하지만 모든 구성요소가 미분 가능하고 weight에 접근할 수 있어야 하므로 API와 tool로 엮인 시스템에는 적용되지 않는다.

ProTeGi (textual gradient for prompts)

\[\pi' = \text{LLM}_{\text{edit}}\!\left(\pi, \text{LLM}_{\text{critique}}(\pi, \text{errors})\right), \qquad \text{beam search over } \pi\]
  • “이 prompt의 어디가 오류를 만드는가?”를 자연어로 얻는다.
  • 하지만 변수가 prompt 하나이고 graph가 한 단계라, 다단계 시스템이나 해 자체의 최적화로 확장되지 않는다.

DSPy (program-level few-shot bootstrapping)

\[\Pi^\ast = \arg\max_{\text{demos} \subset \text{traces}} \bar{\mu}(\Phi(\cdot; \text{demos}))\]
  • “어떤 demonstration 조합이 program의 점수를 올리는가?”를 random search로 찾는다.
  • 하지만 신호가 metric 점수뿐이라 어느 module을 왜 고쳐야 하는지는 담기지 않고, prompt가 길어진다.

TextGrad

\[\frac{\partial \mathcal{L}}{\partial v} = \bigcup_{w \in \mathrm{Succ}(v)} \nabla_f\!\left(v, w, \frac{\partial \mathcal{L}}{\partial w}\right), \qquad v_{\text{new}} = \mathrm{TGD.step}\!\left(v, \frac{\partial \mathcal{L}}{\partial v}\right), \quad v \in \{\text{prompt}, \text{code}, \text{SMILES}, \theta, \dots\}\]
  • “이 변수가 쓰인 모든 맥락에서, 하류의 비평을 감안해 어떻게 고쳐야 하는가?”를 graph의 어느 변수에 대해서든 묻는다.
  • 하지만 비평의 품질이 gradient LLM에 묶여 있고, 한 iteration에 edge 수만큼의 LLM 호출이 든다.

따라서 이 논문의 핵심은 단순히 “LLM에게 prompt를 고쳐 달라고 했다”가 아니다. gradient 연산자와 TGD라는 도메인 무관한 두 meta-prompt로 chain rule과 gradient descent를 텍스트 위에 재정의하고, 최적화 변수를 prompt에서 code, 분자, 치료 계획의 hyperparameter까지 넓혀, PyTorch와 같은 세 줄로 compound AI system 전체를 최적화하게 만든 framework이다.
